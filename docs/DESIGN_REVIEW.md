## 1. 結論（要約）

v1 は**「カードを出してゲージを動かすゲーム」**になっていました。新しく定義された中心体験とはずれています。

> **情報を集め、相手の事情を理解し、そこから新しい解決策を発見すること。**【依頼】

ずれの原因は、次の3つに集約できます。

1. **相手の「事情」がゲームの中に存在しない**。王の利害（国庫・時間・面子）は文章の設定でしかなく、交渉の判定には信頼・緊張・進行度という抽象的な数値しか使われていない。
   → プレイヤーが「相手の事情を理解」しても、それを使う場所がない。
2. **情報から正解カードへの対応が1対1**。「大臣のため息」を取ると「紹介状の提案」カードが手に入り、それを出せば勝ちに近づく。
   → 再設計依頼が明確に避けたいとした「特定の情報を取得すると決まった正解カードが手に入る」仕組みそのもの。
3. **「解決策」が中身ではなく数値として扱われている**。合意は「議題の進行度が必要値に届いたか」で決まり、何を提案したかは判定に関係しない。
   → 新しい解決策を発見する喜びがない。

一方で、v1 には残すべき資産もあります：会話と交渉の分離、Node に依存しない純ロジック層、データ駆動、翻訳キーの方針、シード付き乱数、振り返りの文章ルール。これらは再設計後も引き継ぎます。

## 2. 新コンセプトとの適合性

再設計依頼の体験1〜6に対して、v1 の各要素を評価しました。

| 体験（再設計依頼） | v1 の該当要素 | 評価 | 理由 |
|---|---|---|---|
| 1. 会話や探索で情報を集める | 会話グラフ、質問機会×3、城内NPC | ◯ 合っている | 「何を聞くか」の選択になっており、正誤もない |
| 2. 発言や行動から裏の事情を推測する | なし（情報カードを取ると自動で事実が公開される） | ✕ 合っていない | 推測する余地がない。事情は「公開された／されていない」の二値 |
| 3. 情報から別の解決策を発見する | 情報 → 決まったカードの追加 | ✕ 合っていない | 発見ではなく「入手」。組み合わせによって何かが生まれる仕組みがない |
| 4. 解決策を相手に提案する | カードを議題に対して出す | △ 一部だけ | 提案の中身（何を求め、何を差し出すか）を組み立てる要素がない |
| 5. 相手の反応を見て交渉を進める | 意図表示（拒絶・防御・譲歩・要求強化） | △ 一部だけ | 意図が王の利害と結び付いておらず、抽選された記号に反応するだけ。反応から何かを学ぶことがない |
| 6. 双方が受け入れられる合意を目指す | 結果判定は信頼と議題数で決まる | ✕ 合っていない | 王の満足度を測る仕組みがない。「双方」のうち王の側が判定に存在しない |
| 振り返りで理論とつなぐ | 振り返り画面、概念タグ | ◯ 合っている | 文章ルールはそのまま使える。ただし振り返る対象（判断の中身）が薄い |

## 3. 要素ごとの再評価（再設計依頼 §4 の8項目）

| 要素 | v1 での役割 | 問題 | 判断 |
|---|---|---|---|
| 情報カード | 交渉カードの追加・強化、事実の公開 | 1対1の鍵になっている | **変える**：「手掛かり」にする。単体で答えにはならず、組み合わさって推測（気づき）を生む／提案の材料を開く／交渉中に根拠として示す、の複数の使い道を持たせる |
| 交渉カード（6役割） | AP を払ってゲージや進行度を動かす | 交渉ではなくリソース管理になる | **変える**：カードは「提案の部品（求める／差し出す／形）」と「探り（質問）」にする。役割の考え方（質問・根拠・共通利益・条件交換・選択肢の拡張・信頼回復）は、行動の種類として残す |
| デッキ構築 | 所持カードから12枚を選ぶ | 発見したカードをデッキから外せてしまう／ドローの運で「思いついた解決策を出せない」ことが起きる | **MVPでは削除**。「何を集めたか＝持ち札」とする（探索がデッキ構築の代わり）。企画書§5.2との差分なので要承認（§6） |
| 相手の行動予測 | 意図4種を抽選し、ターン開始時に表示 | 王の事情と無関係なので、読み合いが記号当てになる | **変える**：「反応予測」にする。王の利害を理解しているほど、提案に対する王の反応が事前に見える。さらに、王自身の行動（期限を切る・大臣が口を挟む）を予兆付きで起こす |
| 信頼・緊張などのゲージ | 信頼・緊張・譲歩余力・AP・進行度 | 5種類の数値を管理するゲームになる | **大幅に削減**：「王の忍耐（残りラウンド）」と「王の心証（4段階）」の2つだけにする。どちらも数字ではなく、砂時計と表情で見せる |
| 議題ごとの合意判定 | 進行度が必要値に届いたら合意 | 何に合意したかという中身がない | **変える**：「合意書」の枠（旅の支え／同行者／出発／見返り）に、**具体的な条件**が入る形にする |
| 質問機会の制限 | 謁見中に3回 | 機能はしているが、交渉と別のリソースになっている | **変える**：謁見前の城では「話せるのは2人まで」とする。謁見中の質問は、提案と同じ**忍耐**を消費する（聞くほど提案の機会が減る） |
| 交渉後の振り返り | 判断3つ、別の方向、概念 | 振り返る中身が数値操作になる | **残して強化**：王の本音（利害の重み）を最後に明かす。「持っていた情報だけで成立し得た別の合意」を自動で探して示す |

## 4. v1 仕様の矛盾・不整合

v1 の数値とデータ構造を突き合わせて見つかった問題です。再設計でほとんどの要素がなくなりますが、同じ種類の誤りを繰り返さないために記録しておきます。

| # | 該当箇所（v1） | 問題 | 再設計での扱い |
|---|---|---|---|
| E1 | §3.5 の表と §6.6 の JSON | 合意0・ターン切れ・信頼3以上のとき、表では「決裂」、JSON（`partial` の `when_any` に信頼3以上の単独条件がある）では「部分合意」になる | 結果判定は「上から順に評価し、最初に一致したもの」と明記する。判定条件は1か所（データ）で定義する |
| E2 | §6.6 の `outcomes` | 緊張10による決裂が JSON の判定条件にない。上から評価すると、議題を1つ合意していれば緊張10でも `partial` になる | 決裂（強制終了）は判定より前の終了処理として分ける |
| E3 | §3.2・§3.4.6・§6.6 | 議題が「3つ」と書かれているが、JSON には `funds` と `letter_of_credit` を含む4つがある。`transform_issue` で資金の進行度がどうなるか、`agreed_count` に二重に数えるかが未定義 | 議題の変形という仕組み自体を廃止する。合意書の枠ごとに条件を1つ入れる |
| E4 | §3.4.3 の条件交換 | 進行+3、譲歩時は2倍で+6。必要値3〜4の議題が1枚で合意に届き、相手の意図を読む必要がなくなる | 数値の進行度を廃止する |
| E5 | §6.5 防御の `multiply: 0.5` | 根拠+2 → +1 なら問題ないが、ほかの補正と重なった場合の丸め方が未定義 | 整数だけで計算する。倍率を使わない |
| E6 | §3.4.6 `reveal_chance` | 核となる隠れた事情が確率で公開されるため、中心体験が運に左右される | 情報の取得はすべて決定的にする（乱数を使わない） |
| E7 | §6.5 `concede` の `@target`、`reject` の `@most_advanced` | 対象の決め方が未定義（同点の場合など） | 王の行動は条件付きの台本として定義し、対象を明示する |
| E8 | §3.4.2・§6.6 | 12枚のデッキ、毎ターン5枚まで補充、6ターン。山札が尽きた後の扱い（捨て札の再シャッフル）が未定義 | ドロー自体を廃止する |
| E9 | §3.4.3 と §3.3.2 | デッキ編成で、情報から得たカード（紹介状など）を外せてしまい、獲得した情報が交渉で使えなくなる | デッキ編成を廃止する。得た材料は常に使える |
| E10 | §3.2・§6.6 | 開始時の信頼3と、目標の「信頼3以上」が同じ値。一度でも信頼が下がれば合意しても失敗になり、判定が厳しすぎる | 終了時の心証を勝利条件にしない（評価に使うのは合意の中身） |
| E11 | §3.2 の議題「出発の期限」 | 主人公にとって何を合意すれば得なのかが定義されていない。しかも条件交換「迅速な出発」は、期限で譲ることと期限の議題を進めることを同時に意味している | 出発時期は「明朝／三日以内（既定）／五日の猶予」という具体的な選択肢にし、それぞれの得失を明示する |
| E12 | §3.5「双方納得の合意」 | 「双方」と言いながら、王の側の満足度を測る指標がない | 合意の評価を「主人公側の価値」と「王側の満足」の2軸にする |
| E13 | §8.3 シミュレーション目標 | 「情報なし」の条件が会話の選択（質問機会）と連動しておらず、何を「情報なし」とするかが曖昧 | 手掛かりの組み合わせごとに、到達できる合意を全探索して検証する |
| E14 | §3.3.2「王の口癖」 | 入手に自宅NPCと王への rapport 選択の両方が必要。質問機会3回のうち1回を使っても得られるのは表示精度だけで、ほかと比べて費用対効果が低い | 廃止する（反応予測は利害の理解から自然に生まれるようにする） |
| E15 | §2 F05 とプレイ時間 | 質問機会3回、交渉6ターン、AP3、手札5を合わせると、交渉が長く単調になる可能性がある（15〜25分の見積りに根拠がない） | 交渉は最大6ラウンドで、1ラウンド1行動にする。標準的なプレイの流れでラウンド数を確認する |

## 5. 引き継ぐもの・捨てるもの

**引き継ぐ**
- アーキテクチャ：会話と交渉は実行時の状態データを通してだけつながる／`scripts/core` は Node に依存しない純ロジック／イベント列を返す設計
- データ駆動、翻訳キー（`tr()` と CSV）、IDの命名規則、起動時の参照検証
- シナリオの舞台（王との謁見、国庫の逼迫、紹介状という解決策の芽）
- 振り返りの文章ルール（評価語を使わない、唯一の正解として扱わない）
- 着手順の考え方（交渉コアを画面なしで先に検証する）
- HTML5 での早期検証、日本語フォントへの対応

**捨てる**
- 信頼・緊張・譲歩余力・AP・進行度のゲージ群
- 意図の抽選表、意図による効果倍率
- デッキ編成、ドロー、手札
- 効果オペレーション（`add_progress` など）の語彙
- 確率による情報公開

## 7. 改善方針

1. **相手の事情をゲームの中で表現する**：王に「利害」とその「重み」を持たせ、提案の受け入れはその利害に基づいて決まるようにする。プレイヤーが理解すべきなのは、数値ではなくこの利害の構造である。
2. **情報は鍵ではなく、見え方と組み合わせの材料にする**：1つの手掛かりは単独では答えにならない。組み合わさって「気づき」（推測）になり、推測は確かめられて「確信」になる。どの解決策の材料にも、複数の入手経路を用意する。
3. **解決策は部品を組み立てて提案する**：「何を求めるか × 何を差し出すか × どんな形にするか × 何を根拠にするか」の組み合わせが解決策になる。部品は情報によって増え、組み合わせによって新しい解決策が生まれる。
4. **反応から学べるようにする**：拒否や保留にも、必ず**理由の手掛かり**（表情・視線・言い淀み）を付ける。失敗した提案も情報になる。
5. **数値は2つまで、どちらも見える形で**：王の忍耐（時間の資源）と心証（関係）だけにする。
6. **評価は2軸で、正解は1つにしない**：主人公の得と王の満足で結果を4象限＋既定案に分ける。双方納得にたどり着くルートを3つ以上用意し、それぞれ別の代償を持たせる。
7. **全探索で検証する**：提案の組み合わせは数千通り程度なので、全部を機械的に探索し、「情報なしでも合意できるか」「双方納得のルートは3つ以上あるか」「情報1つだけで双方納得に届く支配的な戦略がないか」を自動テストで保証する。
